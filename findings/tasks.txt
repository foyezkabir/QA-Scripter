Title: Tasks module - one deletion among several rapid back-to-back deletes silently no-ops [dev.app.velaops.ai]
Type: functional
Module: tasks
Description: TestRail case 62203 tests creating 10 tasks and deleting a subset of 4 in quick
  succession, expecting exactly the correct surviving set. Confirmed live, reproduced twice: after
  sequentially submitting Delete -> Yes, delete for 4 tasks back-to-back, exactly one of the four
  remained fully present in the list afterward each time - the other 3 deletes succeeded normally.
  A different task was affected each run ("QA well-documented Task vBjQC2" the first time,
  "QA different Task 7mgHpI" the second) - not a name-specific fluke. Between the two runs, the
  test's own delete helper was hardened to explicitly wait for each card to fully detach from the
  DOM before starting the next task's delete, ruling out a client-side race in the test itself as
  the cause - the second failure happened with that wait already in place. Given this same agent is
  independently documented elsewhere (above) to autonomously create its own background tasks
  concurrently with a UI session's reads/writes, a genuine backend race on the automations list
  under concurrent/rapid writes is the leading explanation.
Steps to reproduce:
  1. Create several tasks on one agent.
  2. Delete 4 of them back-to-back via the UI, confirming each one's dialog fully closes (card
     detaches) before starting the next delete.
  3. Re-check the list afterward.
Actual result: One of the four targeted tasks (a different one each run) was still present; the
  other three were gone - with no error shown to the user at any point.
Expected result: Every confirmed deletion should reliably remove its task, regardless of how
  quickly subsequent deletes are triggered, or the UI should surface a clear error if one fails.
Confidence: high (reproduced twice via a real automated Playwright test - tests/concurrency.spec.ts
  TC-01 - with a client-side race in the test's own code explicitly ruled out between the two runs).
  Follow-up (2026-07-20): a separate one-off cleanup script that deleted 16 leftover test tasks in
  a tight loop (no pause between deletes, closing the browser immediately after the loop finished)
  reported all 16 as successful, but NONE of the 16 had actually persisted when checked via a fresh
  page load moments later - every one was still present. Manually deleting the same tasks one at a
  time through normal interactive use, each confirmed by a full page reload before moving to the
  next, worked reliably for all of them. This strongly suggests deletion is optimistic on the
  frontend (the card is removed from view as soon as "Yes, delete" is clicked, without waiting for
  the backend request to confirm), so anything that closes the tab/browser or navigates away
  shortly after a batch of deletes can lose them silently with zero indication - a real risk for
  any user who deletes several tasks and quickly closes the page.
